# Rent Well (mobile app)

React Native (Expo) property management app for small landlords (1 to 10 units) who manage rentals on the side. One app, two roles: landlord and tenant. It is Christian's project for his Mobile Development course (IS course, runs through December 2026). The landlord side is built first, the tenant side comes after.

The code so far was written in an earlier chat session and has been run only partly. Expect small bugs. Verify imports, exports, and file names before assuming something works.

## Stack
- Expo, React Native, plain JavaScript (no TypeScript)
- React Navigation: native stack, bottom tabs, and drawer (`@react-navigation/bottom-tabs`, `@react-navigation/drawer`, with `react-native-gesture-handler` and Reanimated 4, no babel config needed on SDK 57), `react-native-safe-area-context`
- AsyncStorage for saving, `expo-image-picker`, `expo-file-system` and `expo-sharing` (CSV export, documents), `expo-document-picker`, `@react-native-community/datetimepicker`, `@expo/vector-icons` (Ionicons)
- Fraunces and DM Sans from `@expo-google-fonts/fraunces` and `@expo-google-fonts/dm-sans`, loaded in `App.js` behind the splash (Inter and the pixel font are gone)
- `react-native-svg`, `expo-splash-screen` (the splash through its config plugin, held in `App.js` until the fonts load), `expo-status-bar`
- `expo-calendar` (imported from `expo-calendar/legacy`, the new object API throws in Expo Go) and `expo-local-authentication` (Face ID and Touch ID), both with their config plugins and strings in `app.json`
- Backend: the Firebase Realtime Database through its REST endpoints with plain `fetch`, the only backend (milestone 2). The address comes from `.env` (`EXPO_PUBLIC_FIREBASE_DB_URL`, git ignored, read in `constants/config.js`), `EXPO_PUBLIC_FIREBASE_API_KEY` is optional and unused until Firebase Auth. `.env.example` has placeholders only. The old Express API (sibling repo) is no longer used by the app. No sockets, no push, no uploads.
- Run with `npx expo start -c` (clear the cache after adding or renaming files)
- Checks: `npm run lint` (whole project), `npm test` (runs once, `npm run test:watch` to watch), `npm run format:check`. Format with `npx prettier --write <files>`. Prettier keeps quoted keys as written (`quoteProps: preserve`). Lint has 5 known warnings (react-hooks exhaustive-deps in existing code), the errors were fixed at the start of milestone 2.

## How the data works
- Two modes, picked at Welcome. Demo is fully local and offline: no network request, no account, sample data, nothing saved. Real mode is Firebase: everything a signed-in account sees is read from and written to the Realtime Database. Firebase Auth comes next milestone.
- Accounts (test accounts stand-in): Log In lists `users` and the picked account (id plus a copy) is kept in AsyncStorage under `rent_well_test_account`. `AuthContext` opens signed in from the copy, re-reads the record, and goes to Login if it's gone. It sets `util/data/session.js` so the data modules know who is signed in. Register screens make a test account (no password), tenant sign up uses an invite from `invites` and writes the user, tenancy, conversation, and used invite in one multi-path PATCH.
- No live listeners over REST: `navigation/useRefreshOnFocus.js` reloads a screen's stores quietly when it comes back into view, plus pull to refresh and a reload after every write. An open message thread checks every 8 seconds (`thread_poll_ms`) while focused and in the foreground.
- Every Firebase provider exposes `status` ('loading' | 'ready' | 'error'), an error message, and refresh. `store/useScreenData.js` plus `components/ui/DataScreen.js` (`withDataScreen`) give a screen its loading, error, and banner states. The coverage matrix is `navigation/screenCoverage.js`, tested by `navigation/screenCoverage.test.js`.
- Tenants: `TenantsProvider` gives one interface (`tenants`, `properties`, `invites`, `refresh`, `reloadQuietly`, `fetchTenantDetail`, `addProperty`, `updateProperty`, `deleteProperty`, `createInvite`, `revokeInvite`, `resendInvite`, `assignTenant`, `moveTenancy`, `endTenancy`, leases). Both modes run the pure `demoTenants.js` and `demoLeases.js` actions: the demo on `demo_tenant_data` in `WorkOrdersContext`, Firebase on the landlord's bundle from `getTenantData(owner_id)`, written with `saveTenantDataChanges` (one multi-path PATCH, rollback on failure). A tenant loads their landlord's bundle and reads their own rentals and read-only state from it.
- Rent ledger: `LedgerProvider` remounts on a mode or account change. Demo: five sample ledgers in memory. Firebase: one ledger per tenancy in the same shape, from `getLedgers` (charges, payments, rentSchedules), every change is a `demoLedger.js` action saved with `saveLedgerChange` (rollback on failure). The landlord's load and every pull to refresh run `catchUpLedgers` (rent and late fees from `syncLedger`, each created with `createIfAbsent` under its fixed id `rent-{tenancyId}-{yyyy-mm}` or `late-rent-...`, so it never double charges). A tenant's phone works the month's charges out on screen without writing them. Money is integer cents, balances always come from `deriveLedger`, only confirmed payments count, claims wait for the landlord. `backendVectors.js` keeps the old backend's own cases as parity fixtures.
- Messages: `MessagesContext` remounts whenever the mode or user changes. Firebase reads `conversations` and `messages/{conversationId}` (push ids), sends with one multi-path write (message, last message, the other side's unread count), and marks read with `lastReadAt` and `unreadCount` per user. Demo mode uses `sampleThreads.js` with a fake read receipt and reply, shared by both demo sides.
- Work orders: with an account `RemoteWorkOrdersProvider` (keyed by user) loads `workOrders` (a landlord's by `ownerId`, a tenant's by `tenantUserId`), shows the cached copy first (`rent_well_work_orders_cache_<user id>`), and every action is optimistic with rollback. It adds `deleteWorkOrder` (expenses stay, unlinked), and the form edits every field (a tenant edits their own while Open). `useWorkOrders()` returns it when there is one, plus `is_remote`, `orders_status`, `orders_error`, `orders_from_cache`, `refreshOrders`, `reloadQuietly`, `ensureOrder`, `open_count`, `active_count`.
- Expenses: a Firebase landlord's expenses are in `expenses`. `ExpensesProvider` loads them, caches per user, and `useWorkOrders()` takes its expenses and actions. Saves are optimistic and roll back with an alert. Old phone expenses upload once through `importExpenses` (per row results, one write, `clientId` so a retry never doubles).
- The landlord's trips, documents, checklists, mileage rate, and budgets: `WorkOrdersContext` loads them from Firebase (`mileage`, `documents`, `checklists`, `ownerSettings`) after the phone copy and writes each change as a field-level multi-path PATCH, rolling back with `cloud_error` on failure (`cloud_status`, `refreshCloud`). Recurring rules stay on the phone and the Recurring button is hidden for a Firebase landlord.
- No uploads in Firebase mode: photo, receipt, document file, and scan buttons only show in the demo. Firebase documents are records (`record_only`, no Open / Share).
- Leases: every tenancy carries `lease` (from `leases/{tenancyId}`, status from `deriveLease`). Lease events are in `leaseEvents/{tenancyId}`.
- Profit: always `profitMath.js` on the loaded ledgers and expenses (parity vectors in `profitParity.test.js`).
- Rent reminders: owner only. Both modes use the ported rules (`demoPreview`, `demoSend`). Firebase reads the log from `reminders`, posts the message with `metadata.type` `rent_reminder` in the conversation, then saves the reminder. The demo logs in the demo tenant data. `MessageBubble` shows a "Payment reminder" label that opens Payments.
- Shared state (the course assignment, `ASSIGNMENT_STATE.md`): work orders are the featured Context example. `useWorkOrders()` throws outside the provider. Past Requests and Tenant Profile read the shared orders too (no own fetch). Proof in `navigation/sharedState.test.js`, `store/firebaseProviders.test.js`, and `navigation/firebaseFlows.test.js`, screen list in `docs/shared-state.md`.
- App lock: a signed-in account with the Security switch on is locked on a launch that restores the session and after more than 60 seconds in the background. The demo and signed out never are. The lock covers the navigator instead of unmounting it.
- `WorkOrdersContext` holds orders, expenses, trips, recurring rules, budgets, the mileage rate, documents, and checklists. Screens read it with `useWorkOrders()`.
- Orders and expenses are separate lists. An expense links to an order with `work_order_id`. The context builds `order.expenses` (a small legacy shape: id, amount, description, photo_uri) so work order screens keep working.
- Saved to AsyncStorage under `rent_well_work_orders`, `rent_well_expenses`, `rent_well_extras`, `rent_well_documents`, `rent_well_checklists`. In real mode each key gets `_<user id>` added (`storageKey` in `util/storageKeys.js`) so accounts on a shared phone never see each other's data. With no user (demo, or signed out) the original keys are used, so data saved before accounts existed is still there, untouched. Nothing saves until the load for the current user finishes.
- Demo mode: `startDemo(role)` resets everything to seed data, sets `demo_role` (`owner` or `tenant`), and turns saving off, `switchDemoRole(role)` changes only the side, `exitDemo()` restores saved data first and then turns demo off (and the side back to owner). Any future network call must be skipped while `demo_mode` is true.
- Demo roles: the demo tenant is Sam Rivera at 123 Maple St, Unit 2 (`demo_tenant` in `features/tenants/data/sampleTenants.js`), the landlord Sam talks to is `demo_landlord` in `sampleThreads.js`. Both sides share every list: Sam's reports go into the local orders (property from Sam's active demo tenancy, one local photo), My Repair Requests and Past Repair Requests filter the local orders with `ordersForTenant`, and Sam's rental and read-only state come from the demo tenant data (`TenantsProvider` with `demo_role` tenant). Ending Sam's tenancy on the landlord side turns the tenant side read-only.
- Expense fields: id, amount, category (IRS Schedule E style), date (YYYY-MM-DD), property, vendor, payment_method, is_capital, billed_to_tenant, recovered, notes, receipts (array of uris), work_order_id, optional recurring_id and split_group.
- Capital improvements are kept out of the deductible total and category bars on purpose.
- Order fields: id, title, description, property, tenant, status (Open, In Progress, Resolved), priority (Emergency, Normal, Low), created_at, started_at, resolved_at, notes, contractor, estimate, photo (a `{ uri }` object or a require), preferred_date (YYYY-MM-DD or '', local only, the server has no date field).
- Work order form (week 10): `updateWorkOrder(order_id, changes)` is in the local context and the remote provider. With Firebase a landlord edits every field until Resolved and a tenant edits their own request while it's Open, the same rule as the demo (`editRuleFor`). Leaving a changed form asks "Discard changes?" through `usePreventRemove`.
- Document fields: id, name, category, property, tenant (optional), stored_name, file_name, mime_type, size, added_at, expires_on (optional, Lease and Addendum only), notes, shared_with_tenant (flag only, nothing reads it yet), sample (true only for seed entries with no file).
- Checklist fields: id, property, type (Move-In, Move-Out), tenant, created_at, move_in_id (set when a move-out was started from a signed move-in), completed, signed_by, signed_on, rooms. Room: id, name, items. Item: id, name, done, condition (Good, Fair, Poor, or null), note, photos (array of stored names), move_in_condition and move_in_note (copied from the move-in, used for the "changed since move-in" flag).
- Checklists: real data starts empty, the samples only load in demo mode. Signing sets `completed`, which locks rooms and items (the context ignores edits to a completed checklist). Delete still works. Photos follow the document rule: only the stored name is saved, `checklist_photos/` in the document directory, demo photos in `demo_checklist_photos/` in the cache.
- Document files: save only `stored_name`, never a full URI. iOS changes the app container path between launches and updates, so always rebuild the URI with `getDocumentUri` from `features/documents/utils/documentFiles.js`. Real files live in `documents/` in the document directory, demo files in `demo_documents/` in the cache, which is cleared when a demo starts and exits.

## Code conventions (Christian's)
- Function names in camelCase, variables in snake_case with descriptive names. Components are `function Name(props)` and read `props.something`.
- Comments are casual, first person, short. Keep every existing comment word for word when editing a file.
